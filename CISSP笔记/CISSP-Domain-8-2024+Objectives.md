# [Domain-8](#domain-8-software-development-security) **软件开发安全**

- Domain 8 的考试权重约为 10%，专注于帮助安全专业人员理解和应用软件或应用程序安全性
  - 应用程序可能会带来重大风险，我们需要了解这些风险并与业务需求进行平衡，并实施适当的风险缓解措施；如果公司开发定制软件，定制解决方案可能会带来额外的、独特的风险和漏洞
    - 具有自定义解决方案的组织应留意逻辑弱点（例如缓冲区溢出漏洞），并防范可能使系统容易受到攻击的恶意更改（例如后门）
  - 随着软件开发环境变得越来越复杂，审查这个领域非常重要——这是对组织安全的最大威胁之一

- 在此领域中，您将学习安全设计、构建、测试、操作甚至停用企业应用程序背后的基本原理
- 安全性应成为设计的一部分，并纳入架构中，保护级别基于需求和操作环境

- **验收**：将完整的软件系统正式、结构化地移交给客户组织；通常涉及测试、分析和评估活动
- **认证**：AKA 安全认证是指定认证机构 (DAA) 的正式声明，基于已批准的一套技术、管理和程序保障措施的实施，信息系统被批准在可接受的风险水平下运行
- **ACID 测试**：通过执行原子性、一致性、隔离性和持久性策略来提供数据完整性
- **聚合**：能够组合来自不同来源的非敏感数据以创建敏感信息；请注意，聚合是一个“安全问题”，而推理是一种攻击（攻击者可以将不太敏感的信息组合在一起以获得更高敏感度的信息）
- **任意代码**：攻击者试图欺骗处理器执行的替代指令和数据集
- **缓冲区溢出**：源代码漏洞允许访问分配给缓冲区的存储空间之外的数据位置；可以通过尝试输入大于缓冲区大小的数据来触发
- **绕过攻击**：尝试绕过数据库的前端控制来访问信息
- **认证**：对系统进行全面的技术安全分析，以确保其满足所有适用的安全要求
- **CAB**：变更咨询委员会的目的是审查和批准/拒绝拟议的代码变更
- **公民程序员**：将与工作相关的知识、见解和想法编入（不同程度的）可用软件的组织成员；过程和结果是临时的，难以管理，并且通常缺乏安全考虑
- **代码保护/逻辑隐藏**：防止一个软件单元读取/更改另一软件单元的源代码/中间代码/可执行代码
- **代码重用**：代码重用而不是重新发明它意味着软件单元（过程/对象）使用正确、完整、安全的代码为开发需求提供更高的生产力
- **完全覆盖**：测试软件的所有功能
- **并发**：系统处理多个同时操作的能力；通过锁定机制进行管理，允许授权用户进行更改并在更改完成后解锁数据元素，从而防止冲突
- **对象/内存重用**：系统分配/释放和重用内存/资源作为请求进程的对象；重用时对象中保留的数据是潜在的安全违规（即数据残留）
- **CORBA**：通用对象请求代理架构是一组解决软件和硬件产品之间互操作性的标准，驻留在网络上的不同机器上；通过网络提供对象位置和使用
- **配置控制**：控制对硬件、固件、软件和文档的修改的过程，以保护信息系统在系统实施之前、期间和之后免受不当修改
- **隐蔽通道/路径**：用于通过通常不用于通信的路径传递信息的方法；违反安全政策或要求的通信路径（有意或无意）；基本类型是定时和存储
- **数据污染**：攻击者尝试在字段、记录、事务或文件级别使用格式错误的输入，试图破坏系统的正常运行
- **数据湖**：一个集中式存储库，以本机格式存储大量原始数据，包括结构化、半结构化和非结构化数据；与数据仓库不同，数据湖中的数据在存储时不会被处理或结构化
- **数据挖掘**：依赖于从许多不同实例和类型的数据中提取更深层含义的分析和决策技术；通常应用于数据仓库内容
- **数据建模**：识别系统在操作使用过程中需要输入、创建、存储、修改、输出和销毁的所有数据元素的设计过程；应该是分析和设计的第一步
- **数据保护和数据隐藏**：限制或防止一个软件单元读取或更改另一软件单元的私有数据，或防止数据被主体发现或访问
- **数据类型强制**：语言如何保护开发人员免于尝试对不同类型的数据执行操作，或以可能导致错误结果的方式执行操作
- **数据仓库**：收集数据源，例如单独的内部数据库，为分析、趋势分析和参考提供更广泛的信息基础；还可能涉及组织外部的数据库
- **以数据为中心的威胁建模**：方法和框架侧重于系统的授权移动和数据输入/输出；对应于对组织数据进行分类时保护传输中、静态和使用中的数据
- **防御性编程**：设计/编码允许系统接受可接受但经过净化的数据输入；缺乏防御性编程措施可能会导致任意代码执行、程序被误导到其他资源/位置，或者泄露对攻击者有用的信息
- **设计评审**：应在功能和控制规范开发之后、代码创建之前进行
- **脏读**：当一个事务从数据库中读取由另一个未提交的事务写入的值时，就会发生这种情况；这是一个并发控制问题，违反了 ACID 的 **隔离** 属性
- **紧急属性**：一种查看系统级行为特征（例如安全性和安保）的替代/更强大的方法；有助于为“我们的系统有多安全？”等问题提供更可测试、可衡量的答案。
- **封装**：请注意参见[域 4](https://github.com/jefferywmoore/CISSP-Study-Resources/blob/main/CISSP-Domain-4-2024+Objectives) 中的网络封装（消歧义）；在软件开发和操作使用的所有阶段执行数据/代码隐藏；将数据和方法捆绑在一起是封装的过程（与解包/揭示相反）
- **可执行文件/目标代码**：目标计算机的CPU和其他硬件可以直接执行的机器语言指令集的二进制表示
- **XML**：可扩展标记语言是一组 HTML 扩展，提供网络环境中的数据存储和传输；经常用于将网页与数据库集成； XML 通常嵌入在构成网页元素的 HTML 文件中
- **功能需求**：描述系统必须执行的有限任务或过程；通常可以直接追溯到最终系统设计和构建中的特定元素
- **分层数据库模型**：数据元素和记录以树状父子结构排列
- **实例**：在面向对象编程中，“类的实例”是指从该类创建的特定对象，它是定义对象的特征和行为的蓝图或模板
- **集成产品和流程开发 (IPPD)**：通过使用多学科团队来优化设计、制造和支持流程，同时集成基本采购活动的管理技术
- **基础设施即代码 (IaC)**：它不是将硬件配置视为手动、直接动手、一对一的管理麻烦，而是将其视为要管理的元素的另一个集合，其管理方式与在 DevSecOps 下管理软件和代码相同
- **数据库中的知识发现 (KDD)**：识别数据中有效且有用的模式的数学、统计和可视化方法
- **知识管理**：高效/有效地管理企业中的信息和相关资源，以推动商业智能和决策；可能包括工作流程管理、业务流程建模、文档管理、数据库和信息系统以及基于知识的系统
- **抽象级别**：源代码/设计文档表示底层对象/系统/组件细节的程度；较低级别的抽象通常比高级抽象具有更多细节
- **Living off the land**（基于非恶意软件的勒索攻击）：系统攻击，其中受损的系统/资源用于追求额外的攻击（即攻击者的议程）；鉴于攻击者的方法，反恶意软件防御无法检测/阻止攻击
- **格式错误的输入攻击**：不正确地处理输入数据是代码错误的常见来源，可能导致任意代码执行，或将程序错误定向到其他资源/位置
- **标记语言**：用于在页面/屏幕上表达数据格式或排列的非编程语言；通常是可扩展的，允许用户定义要执行的附加/其他操作
- **元数据**：描述其他数据的格式或含义的信息，可用于提供描述资源和改进信息检索的系统方法
- **移动代码（可执行内容）**：系统发送给其他人的文件，该文件将控制该客户端上系统/应用程序的执行或直接执行
- **修改原型模型**：从应用程序的简化版本开始的系统设计/构建方法；利益相关者的反馈用于改进第二版本的设计；重复此过程，直到所有者/利益相关者对最终产品感到满意
- **网络数据库模型**：数据元素和记录以任意链接方式排列的数据库模型（例如列表、集群或其他网络形式）
- **非功能性需求**：与系统元素不明确一致的广泛特征；许多安全、安保、隐私和弹性要求可以被视为不起作用
- **对象**：一组数据和可用于操作该数据的方法的封装
- **面向对象的数据库模型**：使用类、实例和对象等面向对象的编程概念来组织、构造和存储数据和方法的数据库模型；模式定义数据的结构，视图指定满足用户/安全要求的表、行和列
- **面向对象的安全**：利用面向对象的编程特性（例如封装、继承、多态性和多实例化）的系统安全设计
- **开源软件**：源代码和设计信息是公开的，并且通常使用允许修改和重构的许可证
- **结对编程**：需要两名开发人员一起工作，一个编写代码，另一个审查和跟踪进度
- **传递审查**：通常通过电子邮件或代码审查系统完成，允许开发人员异步审查代码
- **PERT**：使用节点表示里程碑或可交付成果的图表，显示里程碑之间移动的估计时间
- **多实例化**：（字面意思是“多个版本”）创建数据项的新实例（副本），具有相同的标识符或密钥，允许每个进程拥有自己的数据版本；允许系统以不同的安全级别存储同一数据项的多个版本，以防止未经授权的用户“推断”敏感信息的存在；通过仅向用户显示与其权限匹配的版本，可确保低级别用户无法通过系统错误或重复冲突检测到更高级别数据的存在
- **过程式编程**：强调要执行的步骤的逻辑顺序，其中过程是执行特定功能的一组软件，需要特定的输入数据，产生一组特定的输出，并且过程可以调用其他过程
- **查询攻击**：使用查询工具访问可信前端通常不允许的数据，包括查询应用程序控制的视图；也可能是由于使用 SQL 绕过安全控制的格式错误的查询造成的；可以以类似的方式使用对查询的不正确/不完整检查来绕过访问控制
- **勒索攻击**：威胁破坏、否认或未经授权公开发布/再营销私人信息资产的攻击形式；通常涉及加密资产并扣留解密密钥，直到受害者支付赎金
- **重构**：部分或完全重写一组软件以执行相同的功能，但以更简单、更高效或更易于维护的形式
- **回归测试**：测试系统以了解最近批准的修改是否改变了其他批准功能的性能或引入了其他未经授权的行为；针对应用程序运行一组已知输入并与之前生成的结果（由软件的早期版本）进行比较的测试
- **关系数据库模型**：又称关系数据库管理系统（RDBMS），数据元素和记录排列在彼此相关或链接的表中以实现业务逻辑，其中不同结构或类型的数据记录在同一活动中一起需要
- **具象状态传输（REST）**：用于同步网络上不同系统上运行的两个或多个应用程序的活动的软件架构风格； REST 通常通过 HTTP/S 促进这些进程交换状态信息
- **声誉监控**：防御策略，使用网站或 IP 地址的信任声誉作为阻止组织的用户、进程或系统连接到可能的恶意软件或漏洞利用来源的手段；可能是针对零日攻击的唯一真正防御；涉及监控 URL、域、IP 地址或其他类似信息以分离不可信流量
- **运行时应用程序安全保护（RASP）**：由内置于应用程序中的小型代码单元组成的安全代理，可以检测一组安全违规行为；一旦检测到，RASP 代理可以导致应用程序终止，或采取其他保护措施
- **安全评估**：测试、检查和分析以确定系统满足或超过所需安全态势的程度；可以评估竣工系统是否满足其规范中的要求，或者使用中的系统是否满足当前对现实世界安全威胁的看法
- **软件质量保证**：各种正式和非正式的流程，试图确定软件应用程序或系统是否满足其所有预期功能，不执行不需要的功能，不存在已知的安全漏洞，并且不存在插入或其他设计和功能错误
- **SDLC**：软件开发生命周期是一个与构建、部署和支持软件应用程序的一系列步骤执行的任务相关的框架和系统；从规划和需求收集开始，以退役和日落结束；有许多不同的 SDLC，例如敏捷、DevSecOps、快速原型设计，提供不同的方法来定义和管理软件生命周期；
  - SDLC由以下步骤组成：
    - 需求收集：为什么创建软件、它将做什么以及为谁创建
    - 设计：封装软件如何满足需求
    - 开发：创建/编码软件以满足规范，并根据需要与其他系统集成
    - 测试：验证/验证软件是否满足要求
    - 操作和维护：部署并确保其得到适当配置、修补和监控
- **源代码**：使用正式编程语言的语法和语义规则的人类可读形式的程序语句
- **间谍软件/广告软件**：执行各种监控和数据收集功能的软件；又称潜在有害程序/应用程序 (PUP/PUA)，可用于监控员工活动/资源使用（间谍软件）或广告活动（广告软件）；两者都可能是合法的/由系统所有者或不需要的入侵者授权
- **强数据类型**：编程语言的功能可防止数据类型不匹配错误；强类型语言会在编译时产生错误
- **威胁面**：围绕或包含系统元素的边界或周界的总渗透集
- **TOCTOU 攻击**：检查时间与使用时间 (TOCTOU) 攻击利用执行安全检查（例如身份验证或授权）与资产实际使用之间的时间延迟
- **活板门/后门**：又称为维护挂钩；绕过访问控制措施的隐藏机制；架构或系统的入口点，由开发人员在开发过程中插入软件中，以提供获取修改/支持的方法；也可能被攻击者插入，绕过旨在防止未经授权的软件更改的访问控制措施
- **UAT**：用户验收测试通常是测试过程的最后阶段；验证开发的解决方案是否满足用户需求，并根据用例进行验证

## [8.1](#81-understand-and-integrate-security-in-the-software-development-life-cycle-sdlc-osg-10-chpt-20) 了解并集成软件开发生命周期 (SDLC) 中的安全性 (OSG-10 Chpt 20)

- 8.1.1 开发方法（例如敏捷、瀑布、DevOps、DevSecOps、规模化敏捷框架）
  - **敏捷方法**：一种项目管理开发方法，涉及将项目分为多个阶段并强调持续协作和改进；团队遵循计划、执行和评估的循环；重点是迭代开发和频繁反馈以及小型自组织跨职能团队之间的协作
    - 敏捷开发强调：
      - 在短时间内交付工作软件，有助于更快地将软件推向市场
      - 通过频繁测试和提供反馈来降低风险，帮助在开发过程的早期发现和解决问题
    - 敏捷由 17 位先驱者于 2001 年发起，制定了“敏捷软件开发宣言”（[agilemanifesto.org](https://agilemanifesto.org)），阐述了敏捷方法的核心理念：
      - **流程和工具上的个体和交互**
      - **工作软件**优于全面的文档
      - **客户合作** 通过合同谈判
      - **响应变化**而不是遵循计划
    - 敏捷宣言还定义了 12 条原则：
      - 最重要的是通过及早持续交付有价值的软件来满足客户的需求
      - 欢迎不断变化的需求，即使是在开发后期；敏捷流程利用变革为客户带来竞争优势
      - 频繁地交付工作软件，从几周到几个月不等，优先考虑较短的时间范围
      - 业务人员和开发人员必须在整个项目中每天一起工作
      - 围绕积极主动的个人构建项目；为他们提供环境、支持和工具，并相信他们能够构建
      - 强调面对面的交谈
      - 工作软件是衡量进度的主要标准
      - 敏捷流程促进可持续发展；团队应该能够无限期地保持恒定的节奏
      - 持续关注卓越技术和良好设计可增强敏捷性
      - 简单性，或者最大化未完成工作量的艺术，是至关重要的
      - 最好的架构、需求和设计来自自组织团队
      - 团队定期审查其有效性并进行调整以进行改进
    - 已经出现了几种采用这些敏捷原则并围绕它们定义特定流程的方法：
      - **Scrum**：团队用来自我组织并朝着共同目标努力的管理框架；它描述了一组用于高效项目交付的会议、工具和角色，允许团队进行自我管理、从经验中学习并适应变化；根据每日团队会议命名，称为 scrums；开发侧重于交付成品的短冲刺；集成产品团队（IPT）是这种方法的早期成果
      - **看板**：用于管理和跟踪工作流程的可视化系统；看板这个词在日语中的意思是“你可以看到的卡片”；看板团队专注于减少项目（或用户故事）从开始到结束所需的时间，使用看板并不断改进他们的工作流程
      - **快速应用程序开发（RAD）**：一种敏捷的软件开发方法，更多地关注正在进行的软件项目和用户反馈，而不是遵循严格的计划，强调快速原型设计而不是规划； RAD 使用四个阶段：需求规划、用户设计、构建和割接
      - **Rational Unified Process (RUP)**：一种敏捷软件开发方法，将项目生命周期分为四个阶段：
        - 启动：定义项目范围并开发业务案例
        - 细化：规划项目、指定功能并确定架构基线
        - 构建：构建产品
        - 过渡：向用户提供产品
        - 在每个阶段中，都会发生所有六个核心开发学科：业务建模、需求、分析和设计、实施、测试和部署
      - **敏捷统一流程 (AUP)**：合理统一流程的简化版本，它描述了一种简单、易于理解的方法，使用敏捷技术和概念来开发业务应用软件，但仍然忠于 RUP
      - **动态系统开发模型（DSDM）**：一种敏捷的项目交付框架，最初用作软件开发方法；主要原则：
        - 关注业务需求：DSDM 团队建立有效的业务案例并确保整个项目的组织支持
        - 按时交付：工作应该有时间限制且可预测，以建立开发团队的信心
      - **极限编程 (XP)**：一种敏捷项目管理方法，目标是快速、简单、开发周期短，[使用五个指导值和五个规则](http://www.extremeprogramming.org)；刚性结构、集中冲刺和持续集成的目标是更高质量的产品
      - **Scaled Agile Framework® (SAFe)**：一组用于在企业规模实施敏捷实践的组织和工作流程模式；该框架是一个知识体系，包括关于角色和责任、如何规划和管理工作以及要坚持的价值观的结构化指导
  
  - **瀑布**：
    - 一种线性的开发方法，每个阶段都需要在下一阶段开始之前完全完成（例如，水只向下坡或朝一个方向流动）；瀑布模型由 Winston Royce 于 1970 年开发，采用线性顺序生命周期方法；所有项目需求都是预先收集的，随着更多信息的出现，没有正式的方法来整合变更
    - 传统模型有7个阶段，每个阶段完成后，项目就进入下一个阶段；迭代瀑布模型确实允许开发返回到前一阶段以纠正缺陷
      - 系统要求
      - 软件要求
      - 初步设计
      - 详细设计
      - 代码和调试
      - 测试
      - 操作与维护
    - 该模型的一个主要批评是它非常僵化，对于大多数复杂的项目来说并不理想，因为这些项目通常包含许多影响整个项目生命周期范围的变量
  - **螺旋模型**：改进的瀑布模型（由 Barry Boehm 开发），有自己的阶段：(1) 确定目标，(2) 识别和解决风险，(3) 开发和测试，(4) 计划下一次迭代；它是一个风险驱动的开发过程，遵循迭代模型，同时还包括瀑布元素
    - 按照定义的阶段完成，然后重复该过程，类似于螺旋
    - 螺旋模型为瀑布模型的主要批评提供了解决方案，因为它允许开发人员随着技术需求和客户需求的迭代而返回到规划阶段
  - **V-Model**（验证和验证模型），它通过将每个开发阶段与相应的测试阶段配对来扩展瀑布模型； V 模型说明了开发和验证活动之间的并行关系
  - **DevOps（开发和运营）**：一种软件开发、质量保证和技术运营方法，它将孤立的员工联合起来，并将这三个职能整合到一个运营模型中； DevOps 的目标是缩短系统开发生命周期并提供持续交付
    - DevOps 与精益和敏捷开发方法紧密结合，旨在大幅减少开发、测试和部署软件变更所需的时间
    - 使用 DevOps 模型和持续集成/持续交付 (CI/CD)，组织努力每天推出数十次甚至数百次代码
    - 这需要高度自动化，包括集成代码存储库、软件配置管理流程以及开发、测试和生产环境之间的代码移动
    - 开发和运营的紧密结合还需要安全控制的同步整合
    - 安全性必须紧密集成并以同样的敏捷性移动
  - **DevSecOps**：指开发、安全、运维一体化；通过集成安全实践扩展 DevOps
    - 提供分阶段审查（如在瀑布 SDLC 中）与 DevOps 方法的合并，以在开发周期的每个回合将安全性、安全性、弹性或其他新兴属性的需求纳入最终系统中
    - DevSecOps 支持软件定义安全的概念，其中安全控制被主动管理到 CI/CD 管道中

- 8.1.2 成熟度模型（例如，能力成熟度模型（CMM）、软件保障成熟度模型（SAMM））
  - 成熟度模型帮助组织从不一致、非结构化的软件流程转向更可靠、管理良好的流程
  - 注意：能够描述 SW-CMM、IDEAL 和 SAMM 模型
  - 软件工程研究所 (SEI)（卡内基梅隆大学）创建了软件能力成熟度模型（又名软件能力成熟度模型，缩写为 SW-CMM、CMM 或 SCMM）
    - **SW-CMM**：一种管理流程，旨在促进组织开发、维护和使用软件的流程和工作流程的持续改进
    - 所有软件开发都按顺序经历一组成熟度阶段，CMM 描述了软件过程成熟度的基础原则和实践，旨在帮助提高软件过程的成熟度和质量
    - 请注意，CMM 没有明确解决安全问题
    - CMM 的阶段：
      - **级别 1：初始**：流程杂乱无章；通常很少或没有定义的软件开发过程
        - 无关键绩效指标
        - 流程是临时的且不成熟
        - 没有预测项目质量、完成时间等的依据
        - 有限的项目管理
        - 有限的软件开发工具或自动化
        - 高度依赖个人的技能和知识
      - **级别 2：可重复**：在此阶段，引入基本的生命周期管理流程
        - 注重制定项目管理基本政策
        - 项目策划
        - 配置管理
        - 需求管理
        - 分包合同管理
        - 软件质量保证
      - **第 3 级：已定义**：在此阶段，软件开发人员根据一组正式的、记录在案的软件开发流程进行操作；以基本生命周期管理流程和代码重用为标志；包括需求管理、软件项目规划、质量保证和配置管理的使用
        - 标准指南和程序形成文件
        - 同行评审
        - 群体间协调
        - 组织流程定义
        - 组织流程焦点
        - 培训计划
      - **级别4：托管**：在这个阶段，对软​​件过程有更好的管理；特点是使用定量软件开发措施
        - 为软件产品和流程设定量化目标
        - 软件质量管理
        - 量化管理
      - **第 5 级：优化**：在此阶段发生持续改进
        - 流程变更管理
        - 技术变更管理
        - 缺陷预防
  - **软件保障成熟度模型 (SAMM)**：由开放 Web 应用程序安全项目 (OWASP) 维护的开源项目
    - 提供将安全性集成到软件开发和维护流程中的框架，并为组织提供评估其成熟度的能力
    - SAMM 将软件开发与 5 个业务功能相关联：
      - 治理：管理软件开发流程所需的活动
        - 该功能包括以下实践：
          - 战略
          - 指标
          - 政策
          - 遵守
          - 教育
          - 指导
      - 设计：用于定义软件需求和开发软件的过程
        - 该功能包括以下实践：
          - 威胁建模
          - 威胁评估
          - 安全要求
          - 安全架构
      - 实施：构建和部署软件组件以及管理缺陷的过程
        - 该功能包括：
          - 安全构建
          - 安全部署
          - 缺陷管理实践
      - 验证：为确认代码满足业务和安全要求而进行的活动
        - 该功能包括：
          - 架构评估
          - 需求驱动的测试
          - 安全测试
      - 运营：代码发布后在整个软件生命周期中维护安全性所采取的行动
        - 功能包括：
          - 事件管理
          - 环境管理
          - 运营管理
  - **IDEAL 模型**：由 SEI 开发，这是一种使用许多 SW-CMM 属性的软件开发模型，分为 5 个阶段：
    - 启动：概述变更的业务原因、建立支持并分配适用的基础设施
    - 诊断：在此阶段，工程师分析组织的当前状态并提出一般性的变革建议
    - 制定：根据诊断阶段的建议制定具体的行动计划
    - 行动：在此阶段，组织开发解决方案，然后测试、完善和实施它们
    - 学习：不断分析实现这些目标的努力，并根据需要提出新的行动

  - IDEAL 与 SW-CMM：记住 IDEAL 是一个流程改进模型（如何改进），而 SW-CMM 是一个成熟度评估模型（您目前所处的位置）；下表显示了大致的概念一致性

    |理想| SW-坐标测量机 |
    |----------------|---------------|
    |发起|初始|
    |诊断|可重复|
    |建立|定义|
    |代理|托管|
    |学习|优化|

- 8.1.3 操作与维护
  - 一旦交付到生产环境，软件开发人员必须进行任何其他更改以适应意外的错误、漏洞或互操作性问题
  - 他们还必须跟上不断变化的业务流程，并与运营团队（通常是 IT）密切合作，以确保可靠的运营
    - 运营和开发一起将新系统过渡到系统配置的生产和管理
  - 开发团队必须不断提供修补程序、补丁和新版本，以解决发现的安全问题和已识别的编码错误

- 8.1.4 变更管理
  - 变更管理（又名控制管理）在受控环境中监控系统时发挥着重要作用，并具有 3 个基本组成部分：
    - **请求控制**：提供有组织的框架的流程，用户可以在其中请求修改，经理可以进行成本/收益分析，开发人员可以确定任务的优先级
    - **变更控制**：控制系统生命周期中需要发生的特定变更的过程，用于记录必要的变更相关活动；或者提供一个有组织的框架的过程，多个开发人员可以在该框架中创建和测试解决方案，然后再将其部署到生产环境中
      - 变更管理是项目经理对总体流程的责任，而变更控制是开发人员为确保软件或环境在变更时不会中断而采取的措施
      - 变更控制基本上是开发人员用来重新创建用户遇到的情况并分析适当的变更的过程；它提供了一个框架，多个开发人员可以在将解决方案推出到生产环境之前创建和测试解决方案
    - **发布控制**：变更完成后，必须通过发布控制程序批准发布
      - 发布控制的职责之一是确保该过程包括验收测试，确认在代码发布之前对最终用户工作任务的任何更改均已被理解并正常运行

- 8.1.5 集成产品团队（IPT）
  - **综合产品团队 (IPT)**：由美国国防部 (DoD) 引入，作为一种将多功能团队聚集在一起的方法，其单一目标是交付产品或开发流程或政策，并促进并行而非顺序决策
  - 从本质上讲，IPT 用于确保在开发过程中考虑产品、流程或政策的所有方面

## [8.2](#82-identify-and-apply-security-controls-in-development-ecosystems-osg-10-chpts-152021) 识别并应用开发生态系统中的安全控制 (OSG-10 Chpts 15,20,21)

- 应用程序（包括自定义系统）可能会带来重大风险和漏洞，为了防范这些风险和漏洞，在整个系统的开发生命周期中引入安全控制非常重要

- 8.2.1 编程语言
  - 计算机理解 1 和 0（二进制），每个 CPU 都有自己的（机器）语言
  - **汇编语言**：一种使用助记符来表示CPU基本指令集的方式
  - **汇编器**：将汇编语言源代码转换为机器代码的工具
  - 第三代编程语言，如C/C++、Java、Python，被称为高级语言
    - 高级语言允许开发人员编写更接近人类交流的指令
  - **编译语言**：将源代码转换为机器可执行格式
    - 编译后的代码通常不太容易被第三方操纵；然而，由于源代码以编译形式不可见，因此审阅者也更难检测嵌入式后门或其他安全缺陷
  - **反编译器**：将二进制可执行文件转换回源代码
  - **反汇编程序**：转换回机器可读的汇编语言（编译过程中的中间步骤）
  - **解释型语言**：使用解释器来执行；源代码可见；例如Python、R、JavaScript、VBScript
  - **面向对象编程（OOP）**：定义一个软件的对象集，该软件提供一个或多个对象内部的方法，该对象外部的软件可以请求访问；每种方法可能需要特定的投入和资源，并可能产生一组特定的产出；关注交互中涉及的对象
    - OOP 语言包括 C++、Java 和 C#
    - 将 OOP 视为一组对象，可以请求这些对象执行某些操作或表现出某些行为，共同提供系统的功能或能力
    - OOP 有潜力变得更加可靠并减少程序更改错误的传播，并且更适合建模或模仿现实世界
    - OOP 模型中的每个对象都有与可以对该对象执行的特定操作相对应的方法
    - 对象也可以是其他对象的子类，并从其父类继承方法；子类可以使用父类的所有方法，并具有其他特定于类的方法
    - 从安全角度来看，面向对象编程提供了一种黑盒抽象方法
    - 面向对象编程术语：
      - **消息**：与对象的通信或对象的输入
      - **方法**：定义对象操作的内部代码
      - **行为**：对象表现出的结果或输出
        - 行为是通过方法处理消息的结果
      - **类**：来自一组对象的通用方法的集合，定义这些对象的行为
      - **实例**：对象是包含其方法的类的实例或示例
      - **继承**：当一个类（父类或超类）的方法被另一个子类（子类）或对象继承时发生
      - **委托**：一个对象将请求转发给另一个对象或委托
      - **多态**：对象的一种特性，允许它因为外部条件的变化而对同一个消息或方法做出不同的行为响应
      - **内聚**：描述同一类内方法的目的之间的关系强度
        - 如果所有方法都有相似的目的，则具有高内聚性，并且是良好设计的标志
      - **耦合**：对象之间交互的程度
        - 低耦合：意味着更少的交互
        - 较低的耦合提供了更好的软件设计，因为对象更加独立，并且代码更容易排除故障和更新

- 8.2.2 库
  - **软件库**：执行特定任务的预先编写的组件（类、过程、脚本等）集合，对其他组件有用（例如用于加密算法、管理网络连接或显示图形的软件库）
  - 共享软件库包含可重用的代码，提高开发人员效率，减少从头开始编写众所周知的算法的需要；通常作为开源提供
    - 共享库还可能包含许多安全问题（例如 Heartbleed），开发人员应该了解他们使用的共享代码的起源，并随时了解这些库中可能发现的任何安全漏洞

- 8.2.3 工具集
  - 强迫所有开发人员使用相同的工具集可能会降低生产力和工作满意度；然而，让每个开发人员选择自己的工具和环境会扩大组织的攻击面
    - 更好的方法是使用变更咨询委员会来验证开发人员工具要求，评估相关风险；如果获得批准，SEC 团队将监控控制措施
  - 开发人员使用各种工具，其中最重要的工具之一是 IDE（定义如下）

- 8.2.4 集成开发环境
  - **集成开发环境 (IDE)**：软件应用程序、其控制程序、支持数据库、库和工具集，为程序员或团队提供指定、编码、编译、测试和集成代码所需的内容； IDE 为开发人员提供了一个单一环境，他们可以在其中编写代码、测试和调试以及编译代码

- 8.2.5 运行时
  - **运行时环境 (RTE)**：允许跨不同操作系统或平台移植执行代码而无需重新编译（例如 Java 虚拟机 (JVM)）
    - 这就是所谓的可移植代码，需要在各个环境之间进行翻译，RTE的作用

- 8.2.6 持续集成和持续交付（CI/CD）
  - **持续集成和持续交付**：工作流自动化流程和工具有助于减少（如果不是消除的话）软件开发流程步骤之间手动沟通和协调的需要
  - **持续集成（CI）**：所有新代码在开发人员编写后立即集成到系统的其余部分，并将其合并到共享存储库中
    - 此合并会触发一批单元测试
    - 如果合并没有错误，则需要进行集成测试
    - CI 通过尽早且经常识别错误来提高软件开发效率
    - CI 还允许持续交付（CD）的实践
  - **持续交付（CD）**：增量构建可以随时发布的软件产品；由于所有流程和测试都是自动化的，因此可以每天或更频繁地将代码发布到生产环境
    - 请注意，持续交付和持续部署都是基于 CI 的自动化密集型 DevOps 实践；主要区别在于发布过程的最后一步：人为干预
    - 持续交付：代码始终处于可部署状态，但部署到生产需要手动批准步骤
    - 持续部署：每一个通过自动化测试的变更都会自动部署到生产中，无需人工干预
  - CI/CD 依赖于自动化，并且通常依赖于第三方工具，这些工具可能存在漏洞或受到损害
  - 威胁建模、最小特权、深度防御和零信任等安全实践有助于减少对这些工具和系统的可能威胁

- 8.2.7 软件配置管理
  - **软件配置管理（SCM）**：一种在不同时间点识别软件属性并执行有条不紊的变更控制的产品，目的是在整个 SDLC 中维护软件完整性和可追溯性
    - SCM 跟踪配置更改，并验证交付的软件是否包含所有批准的更改
    - SCM 系统管理和跟踪多人对单个主软件存储库所做的修订，提供并发管理、版本控制和同步
    - 软件变更的审核和记录可以通过以下方式降低组织的风险：
      - 提供对软件应用程序所做的所有修改的详细记录
      - 允许安全团队识别可疑活动
      - 快速检测未经授权的更改并调查潜在的安全漏洞
      - 并采取纠正措施，最终保护组织数据和系统的完整性和机密性

- 8.2.8 代码存储库
  - 软件开发是一项协作工作，较大的项目需要开发团队在不同部分同时工作
  - 代码存储库支持协作，充当源代码的中央存储点
    - GitHub、Bitbucket 和 SourceForge 是提供版本控制、错误跟踪、Web 托管、发布管理和通信功能的系统示例

- 8.2.9 应用程序安全测试（例如静态应用程序安全测试（SAST）、动态应用程序安全测试（DAST）、软件组成分析、交互式应用程序安全测试（IAST））
  - **静态应用程序安全测试 (SAST)**：又称静态分析、工具和技术，可帮助识别软件缺陷（例如数据类型错误、循环/结构边界违规、无法访问的代码）或安全策略违规，并通过在不执行程序（或在编译程序之前）的情况下检查代码来执行
    - 术语 SAST 通常保留用于协助分析师和开发人员的自动化工具，而人类的手动检查通常称为代码审查
    - SAST 允许开发人员扫描源代码以查找缺陷和漏洞；它还提供了一种可扩展的安全代码审查方法，并确保开发人员遵循安全编码策略
  - **动态应用程序安全测试 (DAST)**：又称动态分析，是对实时运行的程序进行评估
    - 执行被测软件单元、应用程序或系统的工具，试图驱动它揭示潜在的可利用漏洞
    - DAST 通常在程序清除 SAST 并且基本代码缺陷已修复后执行
    - DAST 使开发人员能够跟踪可能导致安全问题的微妙逻辑错误，而无需创建人为的引发错误的场景
    - 动态分析对于兼容性测试、检测内存泄漏、识别依赖关系以及在不访问软件实际源代码的情况下分析软件也很有效
  - **软件成分分析 (SCA)**：识别代码库中的开源和第三方组件、对其版本和许可证进行分类以及标记已知漏洞的工具和技术； SCA 对于管理软件供应链风险至关重要
  - **交互式应用程序安全测试 (IAST)**：SAST 和 DAST 的组合，此类应用程序测试在运行系统 (DAST) 上完成，并可访问源代码 (SAST)

## [8.3](#83-assess-the-effectiveness-of-software-security-osg-10-chpts-2021) 评估软件安全的有效性 (OSG-10 Chpts 20,21)

- 8.3.1 审核和记录变更
  - 应用程序应配置为将错误和其他安全事件的详细信息记录到集中式日志存储库
  - 开放 Web 应用程序安全项目 (OWASP) 安全编码实践建议记录以下事件：
    - 输入/输出验证失败
    - 身份验证尝试，尤其是失败
    - 访问控制失败
    - 篡改尝试
    - 使用无效或过期的会话令牌
    - 操作系统或应用程序引发的异常
    - 使用管理员权限
    - 传输层安全 (TLS) 故障
    - 密码错误
    - 高风险功能（管理操作或使用管理权限、访问敏感数据、创建/删除系统级对象、数据导入/导出等）

- 8.3.2 风险分析和缓解
  - 风险管理是安全软件开发的核心，特别是在映射已识别的风险和实施的控制方面
    - 这是安全软件开发的一个困难部分，尤其是与审计相关的
  - 威胁建模对于开发团队非常重要，尤其是在 DevSecOps 中
  - 评估人员还对软件开发和风险管理计划之间的联系感兴趣
    - 软件项目应在组织的风险矩阵中进行跟踪，以确保开发团队与更广泛的风险管理工作联系起来，而不是孤立地工作

## [8.4](#84-assess-security-impact-of-acquired-software-osg-10-chpts-1620) 评估所购软件的安全影响 (OSG-10 Chpts 16,20)

- 请注意，SBOM 对于评估所购软件的安全影响变得越来越重要；回顾领域 1，SBOM 提供软件产品中所有组件、库和依赖项的正式记录，使组织能够在新漏洞披露时快速识别受影响的系统
- 8.4.1 商业现货 (COTS)
  - **商业现成 (COTS)**：软件元素，通常是应用程序，作为成品提供（不适合由最终用户或为最终用户进行更改）
  - 最广泛使用的 COTS 软件产品已经过安全研究人员的测试（包括良性和恶意）
    - 研究发现的漏洞和漏洞可以帮助我们了解供应商对安全的重视程度
    - 对于利基产品，您应该研究供应商认证，例如 ISO/IEC 27034 应用程序安全性
    - 除了安全编码认证之外，您还可以寻找整体信息安全管理体系（ISMS）认证，例如ISO/IEC 27001和FedRAMP（这些认证很难获得，并且表明供应商对安全性的重视）
  - 如果您可以与供应商交谈，寻找诸如防御性编程之类的流程，这是一种软件开发最佳实践，意味着随着代码的开发或审查，他们会不断寻找出现问题的机会
    - 例如将所有输入例程视为不可信，除非另有证明

- 8.4.2 开源
  - 开源软件通常在发布时附带许可，允许代码访问和检查，以便开发人员可以查找安全问题
    - 然而，这通常意味着软件不附带任何服务或支持，并且需要内部支持来进行配置和安全测试
    - 这也意味着开源开发者和对手都能够审查漏洞代码
    - 开源软件的最大风险是依赖过时的版本——尤其是共享库
    - 组织应制定流程以确保所有开源软件定期更新，更新方式可能与更新 COTS 的流程不同

- 8.4.3 第三方
  - **第三方软件**：（又称外包软件）是第三方专门为组织制作的软件
    - 第三方软件不被视为 COTS，因为该软件是定制的或定制的
    - 第三方软件可能依赖于开源软件，但由于它是定制的，因此可能有不同或额外的漏洞
    - 最佳实践是使用第三方进行外部审计和安全评估；这应该纳入供应商的合同中，并以通过审核为最终确定软件采购的条件

- 8.4.4 托管服务（例如企业应用程序）
  - **托管服务**：可以包括可从本地资源（例如组织内部）或基于云的服务和资产；随着组织将更多功能转移到云中，他们获得了基于云的便利（例如，只需为按需资源使用付费、轻松扩展等），但由于部分基于云的资源超出了组织的控制范围，因此失去了一定程度的控制权
  
- 8.4.5 云服务（例如软件即服务（SaaS）、基础设施即服务（IaaS）、平台即服务（PaaS））
  - 随着组织继续迁移到云（SaaS、IaaS、PaaS），他们应该增加这些服务的安全评估
  - 云泄露的主要原因仍然是配置错误、访问设置缺乏可见性以及访问控制不力
    - 云服务提供商拥有帮助缓解这些问题的工具，如果组织不具备内部专业知识，则应考虑引入第三方专家来提供帮助
  - **一切即服务 (XaaS)**：统称术语，指通过云解决方案为客户提供价值的任何类型的计算服务

## [8.5](#85-define-and-apply-secure-coding-guidelines-and-standards-osg-10-chpts-2021) 定义和应用安全编码指南和标准 (OSG-10 Chpts 20,21)

- **安全编码指南和标准**：由各种软件和安全专业人员确定的最佳实践，如果正确使用，可以显着减少开发过程中引入的可利用漏洞的数量

- 8.5.1 源代码级别的安全弱点和漏洞
  - 源代码漏洞是一种代码缺陷，为威胁行为者提供了危害软件系统安全的机会
    - 源代码漏洞是由设计或实现缺陷引起的
    - **设计缺陷**：如果开发人员正确执行了所有操作，仍然会存在漏洞
    - **实现缺陷**：开发人员错误地实现了良好设计的一部分
  - OWASP 十大漏洞（[2025 版](https://owasp.org/Top10/2025/)）：
    - 访问控制损坏
    - 安全配置错误
    - 软件供应链故障
    - 加密失败
    - 注射
    - 不安全的设计
    - 认证失败
    - 软件或数据完整性故障
    - 安全日志记录和警报故障
    - 特殊情况处理不当

- 8.5.2 应用程序编程接口（API）的安全性
  - **应用程序编程接口（API）**：指定软件组件与其他组件交互的方式
    - API 通过提供安全控制的简单实现来减少提供安全组件交互的工作量
    - API 通过鼓励软件重用并将更改位置保留在一处来减少代码维护
    - **参数验证**：确保检查任何 API 参数是否格式错误、无效或恶意，有助于确保 API 的安全使用；验证确认应用程序接收的参数值在系统处理之前位于定义的限制内

- 8.5.3 安全编码实践
  - 安全编码实践可以概括为标准和指南
    - **标准**：强制性活动、行动或规则
    - **指南**：建议的行动或操作指南，为不可预见的情况提供灵活性
    - 通过执行安全编码标准和维护反映最佳实践的编码指南，组织大大减少了源代码漏洞
  - 要被视为标准，编码实践必须满足以下条件：
    - 降低特定类型漏洞的风险
    - 在组织的所有软件开发工作中均可强制执行
    - 可验证实施
  - 注意：严格应用安全编码标准是减少源代码漏洞的最佳方法；编码标准确保开发人员始终以某种方式做某些事情，同时避免其他事情
  - 安全编码指南是推荐的实践，但往往不如标准那么具体
    - 例如代码注释格式一致，或保持代码函数简短/紧凑

- 8.5.4 软件定义的安全
  - **软件定义的安全（SDS 或 SDSec）**：一种安全模型，其中防火墙、IDS/IPS 和网络分段等安全功能在 SDN 环境中的软件中实现
    - 这种方法的优点之一是传感器（对于 IDS/IPS 等系统）可以根据威胁动态地重新定位
    - SDS 提供了与物理设备的解耦，因为它将安全功能抽象为可以在任何兼容的物理或虚拟基础设施上运行的软件，这对于支持云服务动态扩展和虚拟化数据中心至关重要
  - DevSecOps 支持软件定义安全的概念，其中安全控制被主动管理到 CI/CD 管道中
